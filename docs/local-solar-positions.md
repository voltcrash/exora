# Local Solar System positions

The diorama computes dated positions entirely in the browser. There is no ephemeris API route,
rate limiter, runtime Horizons dependency, or upstream failure state. The data and solver enter
through the lazy diorama modules, not initial startup. After visiting the diorama online, the
existing service worker can replay its hashed assets offline.

## Method and provenance

All thirteen bodies use the existing elliptic Kepler solver with bundled osculating position and
velocity states every **365 days**, covering 1899–2101 to bracket every supported timestamp in
**UTC 1900-01-01 through 2100-12-31**. For a requested instant, propagate the immediately preceding
and following states independently, then blend the positions with `t²(3−2t)`. This keeps positions
continuous across anchor boundaries and limits long-term drift without an astronomy library.
Coordinates are geometric heliocentric ecliptic J2000, AU, with AU/day velocities. The solver uses
the solar gravitational parameter; it does not integrate planetary perturbations between anchors.
Every output is typed `provenance: "derived"`, including at anchor times.

The original recommendation of a single element set with secular rates was not adopted: the
catalog lacks the full dated orientation/phase data, and JPL's short-range approximate-planet
formula ends in 2050 and does not cover the four small dwarf planets. A local table of osculating
states covers all thirteen with the same tested solver. It costs a lazy data chunk, with no new
runtime dependency. This is an approximate visualization model, **not navigation or an observing
almanac**, and its interpolation is not a new JPL solution.

Data were retrieved from NASA/JPL Horizons API 1.2 on 2026-11-15. Each body retains its source URL,
source solution identifier, and anchor target name in `src/data/solar-orbits.json`. Earth uses the
Earth–Moon barycenter (3) and Pluto uses the Pluto-system barycenter (9), while their displayed
identities remain Earth (399) and Pluto (999). This deliberate approximation avoids extrapolating
their short-period satellite-induced velocity wobble for a year. Comparison fixtures use the
actual body centers, so those offsets are included in the reported error.

## Validation and limits

`solar-orbits.test.ts` compares all thirteen bodies against independent Horizons body-center
vectors at five dates: 1900-01-01, 1950-07-01, J2000, 2050-07-11, and 2100-12-30 (the exact
Julian dates and source URLs are in `src/data/solar-orbits-fixtures.json`). These are independent
requests, not values generated by the local solver. The worst observed three-dimensional position
error among **65 comparisons** is **0.000331346 AU (about 49,569 km)**, Ceres on
2050-07-11 06:00 UTC. That is a sampled maximum, not a guaranteed bound throughout the interval.
The test gate is 0.0005 AU. Annual boundary continuity and invalid-date rejection are tested too.

The initial body-center prototype had a worst error of 0.002960027 AU at Earth. Barycenter anchors
reduced Earth's sampled maximum to 0.000139238 AU and Pluto's to 0.000146047 AU; the remaining
worst case is Ceres. Orbit ribbons remain the catalog's simplified shapes and are labeled
separately from dated positions.

## Reproduce

Use the exact source requests retained in the two JSON files to refresh external raw responses,
then normalize them with the generator. Raw responses and tools need not be committed:

```sh
vpx scripts/build-solar-orbits.mjs /tmp/exora-orbit-responses --download
vp check --fix
vp test apps/website/src/solar-orbits.test.ts
```

Without `--download`, the generator reuses that directory, so regenerating from saved responses
is deterministic. A later Horizons solution can legitimately change the input data: rerun the
comparisons and update the documented maximum before committing a refreshed table. The generator
checks API version, center, frame and finite components; tests check the time grid and coverage.
The runtime never fetches any of these source URLs.
